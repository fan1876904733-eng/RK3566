# 3.7.9.59 — listening, inspection and automatic device connection

## Research before implementation

- Google Cloud's Android VoiceRecorder example separates speech start, last detected voice and silence timeout, and records the selected client sample rate: https://github.com/GoogleCloudPlatform/android-docs-samples/blob/master/speech/Speech/app/src/main/java/com/google/cloud/android/speech/VoiceRecorder.java
- Continuous Android recognition timeout discussion: https://github.com/csdcorp/speech_to_text/issues/619 . This is a related symptom, not proof that its proposed workaround fits our custom PCM recorder. The existing app uses AudioRecord and Baidu REST rather than Android SpeechRecognizer.
- USB serial permission and attachment/reconnection guidance: https://github.com/mik3y/usb-serial-for-android and https://github.com/mik3y/usb-serial-for-android/wiki/FAQ . Permissions still belong to Android; automatic connection cannot bypass a refused grant.
- Camera lifecycle discussion: https://github.com/android/camera-samples/issues/19 . The implementation retains one background camera owner and explicitly yields it to the live preview page, avoiding simultaneous Camera2 opens.
- Official Baidu speech examples checked: https://github.com/Baidu-AIP/speech-demo . The existing service/model is retained; no undocumented model identifier or new paid service is introduced.
- Android preprocessing availability is device dependent: https://developer.android.com/reference/android/media/audiofx/NoiseSuppressor and https://developer.android.com/reference/android/media/audiofx/AcousticEchoCanceler . Both effects are optional and released with the recording session.

## Resulting behavior

The follow-up window lasts 15 seconds while waiting for speech. A visible countdown is shared across pages; once voice is detected it displays a listening state. Silence exits visibly to wake-word mode. Short answers are not stripped of an unconditional 200ms prefix. Only wake-acknowledgement audio uses rate-aware tail trimming. Quiet speech thresholds, bounded silent pre-roll and failed-recognition feedback are improved. Recognition accuracy still needs representative recordings and user validation; it is not claimed to be quantified by these changes.

An inspection first saves visible-light and thermal images to one case and observes received radar readings for three seconds. It stores the real series and phase values in `files/radar_windows/<case-id>.json`, with zero samples explicitly recorded when none arrived. The history details and analysis prompt include the observation-window summary. Deleting a case also deletes its associated radar sequence.

If the mini-host was connected when inspection began, the configured 0.30–0.70s exposure command is issued once, and a newly received authenticated WiFi X-Ray image is archived to the inspection case. Analysis waits for both the radar window and saved X-Ray image. A 30-second image timeout asks whether to wait another 30 seconds or analyze the already collected modalities. Continuing waits only; it never repeats exposure. Cancellation invalidates callbacks and releases the momentary voltage channel. If no mini-host was connected, no exposure is commanded and no X-Ray image wait is introduced.

The current XRY2 protocol provides image timestamps but no end-to-end exposure-request correlation ID or physical exposure acknowledgement. Associating an incoming image with a waiting task is not a measurement of the true exposure time; simultaneous unrelated transfers must be excluded during acquisition.

Startup automatically starts thermal streaming, reconnects a permitted USB radar, requests its permission once if needed, and warms the camera cache outside its live-preview page. The WiFi mini-host client already reconnects and is retained. Background camera frames use a supported size near 640x480; the visible preview continues to use its existing acquisition path. Nothing in automatic connection opens the X-Ray source.

Thermal startup distinguishes a native stream handle from actual received images. A stream with no image for eight seconds is restarted; repeated empty streams back off to thirty seconds. A received image resets the backoff. The current attached thermal device is enumerated and starts without SDK error, but delivered no bitmap during this session. Replugging was requested and is not convenient for the user now, so actual thermal image recovery remains unverified. Alternative vendor callback routes were investigated but are not included as unproven fixes.

## Validation scope

Local checks cover 72 command routes, exposure duration parsing/bounds, PCM trimming with and without a wake acknowledgement, and inspection arrival ordering, 30s boundaries, wait continuation, skip and cancellation. Device checks inspect listening UI, report navigation/reading and echo isolation, and play only the fixed non-sensitive sentence “语音播放测试。” through TTS. They do not upload historical images or reports and do not invoke real inspection, exposure or AI analysis. Final microphone recognition quality, physical X-Ray sequencing, mini-host return traffic and a full cold-boot peripheral test require supervised hardware validation.

Validation on the wireless RK3566: 19 device checks passed; application restart automatically received camera frames and radar readings. Debug assembly and lint passed (zero lint errors; existing warnings remain). GPIO exposure outputs remained released at 255. The test helper is removed after validation. The installed app version is 3.7.9.59 (3849); no uninstall or historical data reset is needed.
